## 为什么不能记一个固定 QPS

Nginx、Redis、MySQL、Tomcat 的吞吐受硬件、请求大小、连接与并发模型、命令或 SQL、持久化、缓存命中率和延迟目标影响。历史笔记里的单机数字缺少这些前提，不能用来作容量承诺。

## 记录一次评估需要哪些信息

| 维度 | 最少记录 |
| --- | --- |
| 环境 | 版本、CPU、内存、磁盘、网络与部署拓扑 |
| 数据 | 数据量、键分布、热点、请求与响应大小 |
| 负载 | 读写比例、并发数、到达速率与持续时间 |
| 结果 | 成功吞吐、错误率、p50/p95/p99 延迟与资源使用 |
| 边界 | 排队、限流、下游容量、故障与恢复影响 |

## 从业务预算推导

先确定峰值到达速率和目标延迟，再检查服务、连接池、数据库和下游的瓶颈。平均在途请求数可用吞吐率乘平均停留时间辅助理解，但不能直接把平均值当成尾延迟容量保证。

本仓库没有新增实际压测结果；性能结论应来自相同环境与负载下的测量。
