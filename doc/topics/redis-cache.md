## Q21 缓存与数据库如何保持一致

类型：方案题。优先级：高。

原理与做法：先说明业务允许多长时间的不一致。常见做法是更新数据库成功后使缓存失效，再由后续读取重建，并设置合理过期时间。但并发读取、删除失败或旧请求回填仍可能造成旧值，所以要结合失效重试、版本和对账等手段分析。强约束的金额、审批和权限判断不能仅依赖可能过期的缓存。缓存首先是性能手段，最终业务事实应有明确的权威来源。

进一步思考：问“延迟双删是否保证强一致”，回答不能。固定延迟难以覆盖所有时序，需要按一致性要求选择机制和验证并发窗口。

## Q22 缓存穿透 击穿和雪崩怎么处理

类型：原理与方案题。优先级：中。

原理与做法：穿透是不应命中的请求持续到数据库，可用输入校验、受控空值缓存或布隆过滤等方式减轻；击穿是热点失效导致并发重建，可按业务使用单飞重建、互斥或有条件的旧值服务；雪崩是大范围同时失效或缓存服务故障，可用过期时间分散、限流和降级控制后端压力。这些方案都需要考虑更新及时性，布隆过滤也要处理误判和数据同步。

进一步思考：问“空值缓存多久”，回答由数据创建频率和可接受延迟决定；不能给所有场景套固定 TTL。

## Q23 Redis 分布式锁能保证什么

类型：方案题。优先级：高。

原理与做法：基本做法需要原子地设置不存在条件和过期时间，并使用唯一持有者标识，释放时原子校验持有者后再删除。但锁租约到期后，原持有者可能还在运行，新的持有者也可能开始工作；主从切换和网络问题也会影响保证。因此对关键业务，我还会让数据库约束、版本检查或由下游校验的 fencing token 保护最终写入。续租降低过期概率，但不能当作绝对正确性的证明。

进一步思考：问“finally 直接 DEL 行不行”，回答可能误删别人新获得的锁。问“加锁就不需幂等吗”，回答锁限制并发，幂等保护重复执行，两者不是同一个问题。资料见 [S16](../references.md#s16)。
